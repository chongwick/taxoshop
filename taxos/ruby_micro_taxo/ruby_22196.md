Description
Ruby 3.4.10 intermittently segfaults while an async-http workload terminates task fibers after truncated chunked HTTP responses. The equivalent workload completed 20 high-churn attempts on Ruby 3.4.9 without a crash. ASan shows a heap-use-after-free: the outgoing fiber's rb_fiber_t is freed by GC while fiber_switch still reads its status on the Fiber#transfer path.
Environment¶
ruby 3.4.10 (2026-06-30 revision 2b0b7728dc) +PRISM [aarch64-linux]
Linux aarch64 Docker image.
async-1.32.1, async-http-0.64.2, and async-pool-0.10.3.
The ASan build uses -fsanitize=address -fno-omit-frame-pointer -g -O0 and has YJIT disabled.
Expected behavior¶
An incomplete chunked HTTP response should fail its async task with EOFError; the VM should not crash while cleaning up the task fiber.
Actual behavior¶
Ruby exits with a segmentation fault in the fiber stack pool:
-- C level backtrace --
fiber_pool_stack_release
fiber_stack_release
fiber_switch
rb_fiber_start
One GDB run on a source-built 3.4.10 reached:
#0 fiber_pool_stack_release (stack=0xffffc4012ea0) at cont.c:770
    pool = 0x0
#1 fiber_stack_release (fiber=0xffffc4012b00) at cont.c:903
#2 fiber_switch (...) at cont.c:2728
We first hit this in a production service; the harness below reproduces the same C-level frames using only async-http against a local server, with no application code.
AddressSanitizer result¶
An ASan build makes the bug deterministic. With 50 in-process request bursts, all five stock 3.4.10 runs report:
ERROR: AddressSanitizer: heap-use-after-free
READ of size 1
    #0 fiber_switch /src/ruby-3.4.10/cont.c:2727
...
freed by thread T2 here:
    cont_free /src/ruby-3.4.10/cont.c:1079
    fiber_free /src/ruby-3.4.10/cont.c:1164
...
previously allocated by thread T3 here:
    fiber_t_alloc /src/ruby-3.4.10/cont.c:1986
SUMMARY: AddressSanitizer: heap-use-after-free
    /src/ruby-3.4.10/cont.c:2727 in fiber_switch
Line 2727 of cont.c is the new FIBER_TERMINATED_P(fiber) condition (see Regression candidate below). Thus the first invalid operation is reading the freed rb_fiber_t object's status. It occurs before fiber_pool_stack_release; the latter is a downstream manifestation when the stale status reads as terminated and the release branch continues. The full report is attached as stock-1.log.
Minimal reproduction harness¶
The attached harness consists of:
repro.rb: local raw HTTP server plus direct async-http client;
Gemfile and Gemfile.lock: pinned async dependencies;
Dockerfile and run.sh: repeat the workload on a stock Ruby image.
Run:
./run.sh 3.4.10 20
This is probabilistic; successful runs are expected. The harness retains a log for every attempt and reports the first interpreter crash.
The workload synchronizes groups of ten failures by default:
FAULT_BARRIER=10 ./run.sh 3.4.10 50
Run the same source comparison under ASan (deterministic):
BATCHES=50 ./run-asan.sh 5
./run.sh 3.4.9 20 completes all 20 attempts without a crash; 3.4.9 predates the 148f263a backport.
Regression candidate¶
Ruby 3.4.10 includes ruby_3_4 commit 148f263a, the backport of dc1777d for Bug #21955.
That changes fiber_switch as follows:
-    if (resuming_fiber && FIBER_TERMINATED_P(fiber)) {
+    if (FIBER_TERMINATED_P(fiber)) {
         fiber_stack_release(fiber);
     }
Fiber#transfer passes a null resuming_fiber, so the old condition short-circuited without reading fiber->status. The new condition dereferences the stale fiber pointer before deciding whether to release its stack.
We have not tested ruby-head/3.5, but the same condition is present there since dc1777d, so we expect it to be affected.
Controlled source comparison¶
The harness also includes:
BATCHES=20 ./run-ab.sh 20
It builds the published Ruby 3.4.10 source twice with the same compiler and workload:
stock 3.4.10;
3.4.10 with only the above condition restored to resuming_fiber && FIBER_TERMINATED_P(fiber).
Build
Attempts
fiber_pool_stack_release crashes
stock 3.4.10
20
4
3.4.10 with Bug #21955 condition reverted
20
0
The stock run also had one additional process abort with:
malloc(): unaligned tcache chunk detected
All 20 reverted-build processes completed successfully. These runs used BATCHES=20, 100 requests per batch, concurrency 20, and a barrier of 10 simultaneous truncated responses. The image is built from the Ruby 3.4.10 release tarball with -O0 -g3 -fno-omit-frame-pointer; the only source difference between the two images is the condition shown above.
The ASan A/B uses BATCHES=50: all 5 stock runs report the above heap-use-after-free, while all 5 reverted runs complete cleanly.
Request¶
Could the fiber maintainers review why a rb_fiber_t can be finalized by GC while fiber_switch still holds it as the outgoing fiber? Reinstating the resuming_fiber guard avoids the dereference on the transfer path, but a proper fix likely needs to ensure that the outgoing fiber remains live through the switch or otherwise avoid reading it after its lifetime ends.

  <p><strong>Description</strong></p>
  <div id="issue_description_wiki" class="wiki" data-quote-reply-target="content">
  <p>Ruby 3.4.10 intermittently segfaults while an async-http workload terminates task fibers after truncated chunked HTTP responses. The equivalent workload completed 20 high-churn attempts on Ruby 3.4.9 without a crash. ASan shows a heap-use-after-free: the outgoing fiber's <code>rb_fiber_t</code> is freed by GC while <code>fiber_switch</code> still reads its status on the <code>Fiber#transfer</code> path.</p>
<a name="Environment"></a>
<h2 >Environment<a href="#Environment" class="wiki-anchor">&para;</a></h2>
<div class="pre-wrapper" data-controller="clipboard"><a class="copy-pre-content-link icon-only" title="Copy" data-action="clipboard#copyPre"><svg class="s18 icon-svg" aria-hidden="true"><use href="/assets/icons-0476c1d7.svg#icon--copy-pre-content"></use></svg></a><pre data-clipboard-target="pre"><code class="text syntaxhl" data-language="text">ruby 3.4.10 (2026-06-30 revision 2b0b7728dc) +PRISM [aarch64-linux]
</code></pre></div>
<ul>
<li>Linux <code>aarch64</code> Docker image.</li>
<li><code>async-1.32.1</code>, <code>async-http-0.64.2</code>, and <code>async-pool-0.10.3</code>.</li>
<li>The ASan build uses <code>-fsanitize=address -fno-omit-frame-pointer -g -O0</code> and has YJIT disabled.</li>
</ul>
<a name="Expected-behavior"></a>
<h2 >Expected behavior<a href="#Expected-behavior" class="wiki-anchor">&para;</a></h2>
<p>An incomplete chunked HTTP response should fail its async task with <code>EOFError</code>; the VM should not crash while cleaning up the task fiber.</p>
<a name="Actual-behavior"></a>
<h2 >Actual behavior<a href="#Actual-behavior" class="wiki-anchor">&para;</a></h2>
<p>Ruby exits with a segmentation fault in the fiber stack pool:</p>
<div class="pre-wrapper" data-controller="clipboard"><a class="copy-pre-content-link icon-only" title="Copy" data-action="clipboard#copyPre"><svg class="s18 icon-svg" aria-hidden="true"><use href="/assets/icons-0476c1d7.svg#icon--copy-pre-content"></use></svg></a><pre data-clipboard-target="pre"><code class="text syntaxhl" data-language="text">-- C level backtrace --
fiber_pool_stack_release
fiber_stack_release
fiber_switch
rb_fiber_start
</code></pre></div>
<p>One GDB run on a source-built 3.4.10 reached:</p>
<div class="pre-wrapper" data-controller="clipboard"><a class="copy-pre-content-link icon-only" title="Copy" data-action="clipboard#copyPre"><svg class="s18 icon-svg" aria-hidden="true"><use href="/assets/icons-0476c1d7.svg#icon--copy-pre-content"></use></svg></a><pre data-clipboard-target="pre"><code class="text syntaxhl" data-language="text">#0 fiber_pool_stack_release (stack=0xffffc4012ea0) at cont.c:770
    pool = 0x0
#1 fiber_stack_release (fiber=0xffffc4012b00) at cont.c:903
#2 fiber_switch (...) at cont.c:2728
</code></pre></div>
<p>We first hit this in a production service; the harness below reproduces the same C-level frames using only async-http against a local server, with no application code.</p>
<a name="AddressSanitizer-result"></a>
<h2 >AddressSanitizer result<a href="#AddressSanitizer-result" class="wiki-anchor">&para;</a></h2>
<p>An ASan build makes the bug deterministic. With 50 in-process request bursts, all five stock 3.4.10 runs report:</p>
<div class="pre-wrapper" data-controller="clipboard"><a class="copy-pre-content-link icon-only" title="Copy" data-action="clipboard#copyPre"><svg class="s18 icon-svg" aria-hidden="true"><use href="/assets/icons-0476c1d7.svg#icon--copy-pre-content"></use></svg></a><pre data-clipboard-target="pre"><code class="text syntaxhl" data-language="text">ERROR: AddressSanitizer: heap-use-after-free
READ of size 1
    #0 fiber_switch /src/ruby-3.4.10/cont.c:2727
...
freed by thread T2 here:
    cont_free /src/ruby-3.4.10/cont.c:1079
    fiber_free /src/ruby-3.4.10/cont.c:1164
...
previously allocated by thread T3 here:
    fiber_t_alloc /src/ruby-3.4.10/cont.c:1986
SUMMARY: AddressSanitizer: heap-use-after-free
    /src/ruby-3.4.10/cont.c:2727 in fiber_switch
</code></pre></div>
<p>Line 2727 of <code>cont.c</code> is the new <code>FIBER_TERMINATED_P(fiber)</code> condition (see Regression candidate below). Thus the first invalid operation is reading the freed <code>rb_fiber_t</code> object's status. It occurs before <code>fiber_pool_stack_release</code>; the latter is a downstream manifestation when the stale status reads as terminated and the release branch continues. The full report is attached as <code>stock-1.log</code>.</p>
<a name="Minimal-reproduction-harness"></a>
<h2 >Minimal reproduction harness<a href="#Minimal-reproduction-harness" class="wiki-anchor">&para;</a></h2>
<p>The attached harness consists of:</p>
<ul>
<li><code>repro.rb</code>: local raw HTTP server plus direct async-http client;</li>
<li><code>Gemfile</code> and <code>Gemfile.lock</code>: pinned async dependencies;</li>
<li><code>Dockerfile</code> and <code>run.sh</code>: repeat the workload on a stock Ruby image.</li>
</ul>
<p>Run:</p>
<div class="pre-wrapper" data-controller="clipboard"><a class="copy-pre-content-link icon-only" title="Copy" data-action="clipboard#copyPre"><svg class="s18 icon-svg" aria-hidden="true"><use href="/assets/icons-0476c1d7.svg#icon--copy-pre-content"></use></svg></a><pre data-clipboard-target="pre"><code class="sh syntaxhl" data-language="sh">./run.sh 3.4.10 20
</code></pre></div>
<p>This is probabilistic; successful runs are expected. The harness retains a log for every attempt and reports the first interpreter crash.</p>
<p>The workload synchronizes groups of ten failures by default:</p>
<div class="pre-wrapper" data-controller="clipboard"><a class="copy-pre-content-link icon-only" title="Copy" data-action="clipboard#copyPre"><svg class="s18 icon-svg" aria-hidden="true"><use href="/assets/icons-0476c1d7.svg#icon--copy-pre-content"></use></svg></a><pre data-clipboard-target="pre"><code class="sh syntaxhl" data-language="sh"><span class="nv">FAULT_BARRIER</span><span class="o">=</span>10 ./run.sh 3.4.10 50

<p>Run the same source comparison under ASan (deterministic):</p>
<div class="pre-wrapper" data-controller="clipboard"><a class="copy-pre-content-link icon-only" title="Copy" data-action="clipboard#copyPre"><svg class="s18 icon-svg" aria-hidden="true"><use href="/assets/icons-0476c1d7.svg#icon--copy-pre-content"></use></svg></a><pre data-clipboard-target="pre"><code class="sh syntaxhl" data-language="sh"><span class="nv">BATCHES</span><span class="o">=</span>50 ./run-asan.sh 5

<a name="Regression-candidate"></a>
<h2 >Regression candidate<a href="#Regression-candidate" class="wiki-anchor">&para;</a></h2>
<p>Ruby 3.4.10 includes ruby_3_4 commit <a href="https://github.com/ruby/ruby/commit/148f263a0d299e4532c753470a282144c9104820" class="external"><code>148f263a</code></a>, the backport of <a href="https://github.com/ruby/ruby/commit/dc1777d01770ab62ec99ff6fa4cf622098f44968" class="external"><code>dc1777d</code></a> for <a href="https://bugs.ruby-lang.org/issues/21955" class="external">Bug #21955</a>.</p>
<p>That changes <code>fiber_switch</code> as follows:</p>
<div class="pre-wrapper" data-controller="clipboard"><a class="copy-pre-content-link icon-only" title="Copy" data-action="clipboard#copyPre"><svg class="s18 icon-svg" aria-hidden="true"><use href="/assets/icons-0476c1d7.svg#icon--copy-pre-content"></use></svg></a><pre data-clipboard-target="pre"><code class="diff syntaxhl" data-language="diff"><span class="gd">-    if (resuming_fiber &amp;&amp; FIBER_TERMINATED_P(fiber)) {
</span><span class="gi">+    if (FIBER_TERMINATED_P(fiber)) {
</span>         fiber_stack_release(fiber);
     }
</code></pre></div>
<p><code>Fiber#transfer</code> passes a null <code>resuming_fiber</code>, so the old condition short-circuited without reading <code>fiber-&gt;status</code>. The new condition dereferences the stale <code>fiber</code> pointer before deciding whether to release its stack.</p>
<p>We have not tested ruby-head/3.5, but the same condition is present there since <code>dc1777d</code>, so we expect it to be affected.</p>

The image is built from the Ruby 3.4.10 release tarball with <code>-O0 -g3 -fno-omit-frame-pointer</code>; the only source difference between the two images is the condition shown above.</p>
<p>The ASan A/B uses <code>BATCHES=50</code>: all 5 stock runs report the above heap-use-after-free, while all 5 reverted runs complete cleanly.</p>
<a name="Request"></a>
<h2 >Request<a href="#Request" class="wiki-anchor">&para;</a></h2>
<p>Could the fiber maintainers review why a <code>rb_fiber_t</code> can be finalized by GC while <code>fiber_switch</code> still holds it as the outgoing fiber? Reinstating the <code>resuming_fiber</code> guard avoids the dereference on the transfer path, but a proper fix likely needs to ensure that the outgoing fiber remains live through the switch or otherwise avoid reading it after its lifetime ends.</p>

#### Description

```text
This PR:

* Counts number of actually tracked objects, instead of trackable objects. This ensures that untracking tuples has the desired effect of reducing GC overhead
* Does not track most untrackable tuples during creation. This prevents large numbers of small tuples causing excessive GCs.

For the [example in the original report](https://github.com/python/cpython/issues/139951#issue-3505571273) this makes performance on main a bit better than 3.13.

Benchmarking results show this is about neutral on performance otherwise.
```

```text
It seems that your example abuses the GC.
If you set `gc.set_threshold(2000*2000)`, for example, you will get a better result.

After some digging, I found the following.
1. The default value for the first GC threshold is 2000.
2. Each innermost cycle creates a few tuples.
3. These tuples are short-living and will be destroyed in either `BINARY_OP` or `STORE_SUBSCR`
4. Creating each tuple increments the value of `gc.young.count`.
5. And this is a problem because `gc.young.count` grows until it reaches `gc.threshold[0]` value, at which point the GC will be scheduled
6. At the end of the loop iteration (after `JUMP_BACKWARD`) the scheduled GC will be run.
7. In your example, you get a lot of GC runs despite the short-lived tuples.

Where is the problem?

In the `tuple_dealloc`:
https://github.com/python/cpython/blob/13e9c2d18de26a590f9b11b1add637200bf66dd1/Objects/tupleobject.c#L215-L218

There is a condition that checks the freelist and calls `tp_free` under certain conditions. `tp_free` for PyTuple is a `PyObject_GC_Del` which decrements the value of `gc.young.count`. 

For some reason, the condition is false in our case, so we don't call `PyObject_GC_Del` and don't decrement `gc.young.count`.

I don't yet know how to fix this. However, I will investigate further.
```

### Comment 6 — sergey-miryanov, 2025-10-14T12:18:50Z

Source: [https://github.com/python/cpython/issues/139951#issuecomment-3401505478](https://github.com/python/cpython/issues/139951#issuecomment-3401505478)

```text
Ok, I studied a bit further how freelists work. 
So `tuple_dealloc` works as expected.

What is going on:
Runtime has a set of freelists for tuples (for different sizes - from 1 to 10), size of the each freelist for tuples are 2000 elements.

When we create new tuple, we call `tuple_alloc` and if freelist has available items - we get one and use it.

In our case we create 4 tuples on each iteration. One of them we store as a key in our dict. Other 3 tuples are short-living and `tuple_dealloc` called for them and they returned to freelist. But we took 4 and return 3. This leads to the situation when after some iteration there are no available items in freelist and we create new one with `PyObject_GC_NewVar` and incref `gc.young.count`.

Created tuple then will be returned to the freelist. And after some repetitions of this situation, we get `gc.young.count == 2000` and GC will be scheduled and run.

When we run the schedule GC then the incremental version is called. The incremental version has to check local variables/frames and mark live objects and exclude them from the list to process.

So, we run the GC in our cycles may times. Each run will check the local `d` dict and all keys and values of it. On each run we have to check more and more keys.

This is a problem as I see it. And @pgdr right about bisected commit.

There are two approaches to work around the problem for now - disable the GC before and enable after filling the local dictionary. Or change the value of the first threshold for more appropriate value.
```

### Comment 13 — nascheme, 2025-10-15T17:53:20Z

Source: [https://github.com/python/cpython/issues/139951#issuecomment-3407619259](https://github.com/python/cpython/issues/139951#issuecomment-3407619259)

```text
Yeah, the free-threaded GC is quite different in terms of design and has different performance behavior.  The example code creates many small tuple objects (approximately 4 million) and that causes many GC runs.  For the default build, the GC changed quite significantly between versions 3.13 and 3.14 (see GH-108362).  

In 3.13, there are three generations of container objects (of which tuples are a member of).  Because the tuples in this code contain ints and therefore cannot create reference cycles, the GC "untracks" them when they are encountered.  Because the 2nd and 3rd generation of objects is not growing much, Python 3.13 mostly does many fast first generation collections.

Python 3.14 does away with the generations and uses an "incremental" collector design.  Mark would be the best person to explain what's going on there.  My guess is that for this particular allocation pattern, the 3.14 default GC does more work and therefore ends up slower.

For the free-threaded build, there is no concept of generations or of incremental collection.  Each time the GC runs, it does a full collection.  So, in the cases it gets triggered often, due to many new containers being allocated, it can perform worse.  Python 3.14 includes a resident memory size check (https://github.com/python/cpython/pull/133399) which appears to be helping here.  Running with 3.13t is much slower, probably due to many more collections being done.  

I suspect porting the memory size check to the default GC would help a lot here.  The tuples are small and so process memory use is increasing slowly.  It's also possible that some additional tuning can be done to make the incremental GC work a bit faster.  My guess (would need some deeper study to confirm) is that the key is that nearly all the new container objects are being untracked.  In 3.13 that means that many gen0 collections happen but it doesn't result in more gen1 or gen2 collections.  For the incremental collector, maybe it still ends up examining more of the older objects due to the GC running more often.
```

```text
Yeah, for my it is expected.

If you run `gc.collect(0)` - you run collection of the young generation. In your case there are little to collect.
```

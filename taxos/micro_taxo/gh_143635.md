### Original Issue

Source: [https://github.com/python/cpython/issues/143635](https://github.com/python/cpython/issues/143635)

````text
### What happened?

`types.GenericAlias.__repr__` walks its type arguments by borrowed pointers. A crafted argument object implements `__getattr__` to clear the shared list when `_Py_typing_type_repr` probes `__origin__`/`__args__`, dropping the last reference to the same object mid-repr. The second attribute probe then dereferences the freed object inside `PyObject_HasAttrWithError`, producing a heap use-after-free during `repr()`.

**Proof of Concept:**

```python
import types


class Zap:
    __slots__ = ("container",)

    def __init__(self, container):
        self.container = container

    def __getattr__(self, name):
        if name == "__origin__":
            self.container.clear()
            return None
        if name == "__args__":
            return ()
        raise AttributeError


params = []
params.append(Zap(params))
alias = types.GenericAlias(list, (params,))
repr(alias)
```
````

```text
Hi @picnixz,

Thank for pointing this out and I want to explain more about my understanding of the bug here.

In programming, as far as I know, reentrancy is a property of a program, routine, or function that describes whether it can be safely called again before its previous invocation has completed. In general, a "reentrant function" means it can handle concurrent or nested executions without different interfering with each other [1, 2], which quite a strict criteria.

[1] https://en.wikipedia.org/wiki/Reentrancy_(computing)
[2] https://stackoverflow.com/questions/2799023/what-exactly-is-a-reentrant-function

In the security field, reentrancy refers to a concept similar to the programming definition, but focuses on the security implications of the *re-entry* behavior: what happens when a non-reentrant function is called again before its previous invocation has completed. When describing "reentrancy attacks" or "reentrancy vulnerabilities", the term typically refers to how such non-reentrant function invocations or calls can lead to dangerous consequences.

Most well-known reentrancy vulnerabilities appear in the blockchain field. The infamous DAO attack is a classic example of a reentrancy vulnerability. A simplified case can be found in Fig.1 in [3], which shows how a method in a smart contract can be abused by being re-entered multiple times, leading to financial loss.

[3] https://ieeexplore.ieee.org/stamp/stamp.jsp?tp=&arnumber=10172623

Later, security researchers soon found that reentrancy vulnerabilities can be exploited differently: the re-entered function does not need to be the original function, but can be other functions that share state with the original function. Examples of this pattern are shown in [4-5]. Therefore, the reentrancy vulnerability's concept has been broadened. The previous DAO-like vulnerability is referred to as "self-reentrancy" or "single-function" reentrancy and the newly-found ones are called "cross-function reentrancy" vulnerabilities [6]. As these examples show, the core concept is no longer describing whether the original function is reentrant or not, but how the re-entry behavior to the same function or to functions in the same contract can lead to security issues.

[4] https://medium.com/valixconsulting/solidity-smart-contract-security-by-example-04-cross-function-reentrancy-de9cbce0558e
[5] https://dl.acm.org/doi/pdf/10.1145/3597503.3639153
[6] https://ieeexplore.ieee.org/stamp/stamp.jsp?tp=&arnumber=11102145

Beyond blockchain reentrancy vulnerabilities, CWE-1265 (Unintended Reentrant Invocation of Non-reentrant Code Via Nested Calls) [7] describes a similar case in software security. Its standard description states that "the product invokes code that is believed to be reentrant, but the code performs a call that unintentionally produces a nested invocation of the non-reentrant code." However, in many cases, developers do not even assume whether the function is reentrant or not. Its extended description provides a more boarder characterization: "a weakness is present when one of the possible code paths resulting from a function call alters program state that the original caller assumes to be unchanged during the call."

[7] https://cwe.mitre.org/data/definitions/1265.html

In Python interpreters, and even most of script engines, we observe the refered concrete scenario: when an opcode handler dispatched from an interpreter frame invokes user-overridden/overwritten/provided code, such bytecode gets interpreted again, causing the interpreter frame to be entered twice. The second (nested) interpretation may violate assumptions held by the first opcode handler and lead to memory safety issues. We refer to bugs caused by this behavior as "reentrant interpretation", in respect to the original CWE's "reentrant invocation". 

That said, I admit the terminology has some ambiguity (programming vs. security) and the term "reentrant" in the issue title may be misleading, as it might suggest whether the function itself is reentrant or non-reentrant, rather than describing the security issue arising from the re-entry behavior. I would like to update all of them when I am more available.

Thank you!
```

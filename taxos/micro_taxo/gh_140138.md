### PR #130649: gh-124878: Fix race conditions during interpreter finalization

- URL: [https://github.com/python/cpython/pull/130649](https://github.com/python/cpython/pull/130649)
- State: closed; merged: 2025-03-06T15:38:37Z; merge commit: [`052cb717f5f9`](https://github.com/python/cpython/commit/052cb717f5f97d08d2074f4118fd2c21224d3015)
- Author: colesbury

#### Description

```text
The PyThreadState field gains a reference count field to avoid issues with PyThreadState being a dangling pointer to freed memory. The refcount starts with a value of two: one reference is owned by the interpreter's linked list of thread states and one reference is owned by the OS thread. The reference count is decremented when the thread state is removed from the interpreter's linked list and before the OS thread calls `PyThread_hang_thread()`. The thread that decrements it to zero frees the `PyThreadState` memory.

The `holds_gil` field is moved out of the `_status` bit field, to avoid a data race where on thread calls `PyThreadState_Clear()`, modifying the `_status` bit field while the OS thread reads `holds_gil` when attempting to acquire the GIL.

The `PyThreadState.state` field now has `_Py_THREAD_SHUTTING_DOWN` as a possible value. This corresponds to the `_PyThreadState_MustExit()` check. This avoids race conditions in the free threading build when checking `_PyThreadState_MustExit()`.
```

```text
> I think this needs a similar fix as https://github.com/python/cpython/pull/130649 which is to add reference counting to interpreter states so that the interpreter state cannot be free prematurely before daemon threads are hung.

I don't think this is an actual bug in practice. A thread doesn't need the interpreter to be valid in order to hang; all it needs is to read a single field on the thread state, which is atomically set by a finalizing interpreter (see [`_PyThreadState_MustExit`](https://github.com/python/cpython/blob/9a87ce8b57f5d698900d84b4f6f5aa47b5f37a89/Python/pystate.c#L3009)). Because of Sam's patch that you linked, a thread could try to reacquire the GIL long after the interpreter has been deallocated, but it will still correctly hang.

In the `drop_gil` case that TSan is complaining about, I'm mostly sure it's a false positive, because the interpreter shouldn't be able to finalize in another thread when it doesn't hold the GIL.

As far as I can tell, the only way to actually trigger this is to create a thread state for an interpreter that is already finalizing and has already marked all other threads as "shutting down", but at that point, you're compromising thread-safety anyway, because we assume that there's only one thread left after calling `_PyThreadState_DeleteList`. 

Unless I missed a case where we call `_PyThreadState_MustExit` in an unsafe manner, I'm not convinced we should make finalization even more complicated to somewhat support something that people shouldn't do anyway. Play stupid games with finalization, win stupid crashes!
```

````text
The race is real, not a false positive. The issue is in the very first line of `drop_gil()`:
```c
struct _ceval_state *ceval = &interp->ceval;
```
The daemon thread reads `interp->ceval` while the main thread is freeing the interpreter memory via `free_interpreter() `→ `PyMem_RawFree()` → `memset()`.

Timeline:
1. Main thread: `PyInterpreterState_Delete()` → `free_interpreter()` starts
2. Daemon thread: wakes from `time.sleep()` → `drop_gil()` → reads `interp->ceval`
3. Race: daemon reads from memory being freed by main thread

The `_PyThreadState_MustExit` check you mentioned happens in thread state, but `drop_gil()` accesses interpreter state first. The refcount ensures `PyInterpreterState` stays alive until all thread states (including daemons) are freed.
````

````text
# Bug report

### Bug description:

`list___sizeof___impl` uses atomic read, but `list_clear_impl` and `list_resize` uses non-atomic write. 

reproducer:
```python
from threading import Thread

L = []

def test1():
    for _ in range(100):
        L.append(1)
        L.pop()

def test2():
    for _ in range(100):
        L.__sizeof__()

threads = []
for _ in range(4):
    threads.append(Thread(target=test1))
    threads.append(Thread(target=test2))

for t in threads:
    t.start()
for t in threads:
    t.join()
```
````

````text
It's not entirely necessary to use `list_capacity`, but it will keep some constraints on the implementation that I think are helpful for the list implementation. Right now in the free threading build (with the exception of the broken `list___sizeof___impl`), `PyListObject.capacity` is only written while the lock is held. It's never read. It's only used for compatibility with C API extensions; otherwise we'd not include it in `Py_GIL_DISABLED` builds. Internally, we only use `list_capacity()` to determine the number of allocated elements.

`list_capacity` requires that the passed in array isn't `NULL`. So something like:

```c
    size_t res = _PyObject_SIZE(Py_TYPE(self));
#ifdef Py_GIL_DISABLED
    PyObject **ob_item = _Py_atomic_load_ptr(&self->ob_item);
    if (ob_item != NULL) {
        res += list_capacity(ob_item) * sizeof(PyObject *);
    }
#else
    res += (size_t)self->allocated * sizeof(void*);
#endif
```
````

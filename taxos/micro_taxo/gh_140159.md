#### Description

```text
This PR implements `os.statx`, an interface to the [Linux `statx(2)` system call](https://man.archlinux.org/man/statx.2) introduced in kernel version 4.11 (April 2017) and first available in glibc version 2.28 (August 2018).  This is derived from my earlier PR #136334 with the changes to `os.stat` removed, plus other changes (see below).

---

This PR implements the return value of `os.statx` with a custom C type `statx_result`, which contains a `struct statx` and uses member and getset descriptors to lazily create Python objects on attribute access.  In a comment on the previous PR, @vstinner suggested using `types.SimpleNamespace` as the return value.  I implemented that on [the statx-simplenamespace branch in my fork](https://github.com/jbosboom/cpython/commit/c80787ce3a1433ea831e20fb427f3209317a9783).  Using the benchmarks from [this script](https://gist.github.com/jbosboom/020cb7a5b7241b61e796928850348a72) (note they are not all fair comparisons):

| Benchmark                          | statx-nocache | namespace         |
|------------------------------------|:------------:|:---------------------:|
| statx-sizemtime-mask-size-mtimens  | 1.86 us      | 3.07 us: 1.65x slower |
| statx-basic-all                    | 2.29 us      | 4.57 us: 1.99x slower |
| statx-everything-all               | 2.61 us      | 6.34 us: 2.43x slower |

It's slower than this PR when only size and mtime are requested, because it creates objects for the unconditionally valid members and both the float-seconds and int-nanoseconds timestamps.  We could get some of this back by defining our own mask bits (bit 32 and above).  As more bits are set in the mask and attributes are accessed, the gap widens.  I'm not sure if that's due to dict resizing or slower attribute access or both, and I don't see how to improve either.  The advantage of the namespace implementation is its simplicity, and any speed hacks would dilute that.

(Also, because it doesn't create unrequested members, it's not a perfect wrapper around the system call.  For "real" use it doesn't matter, but for testing the syscall, you'll miss some quirks.  For example, btrfs seems to always return atime and btime, but returns mtime and ctime (always together) only if mtime and/or ctime were requested.)

---

In this PR, most attributes are implemented with member descriptors pointing into the `struct statx` or a member in `statx_result`, so each attribute access on `statx_result` creates a new int or float object.  My previous PR cached the created objects in the `statx_result` for the commonly-used attributes to avoid creating them more than once, which requires getset descriptors.  Obviously, creating objects has a cost, but getset descriptors are slower than member descriptors.  The crossover point turns out to be about two accesses (per attribute).  If an attribute is only used once, this PR is faster; twice, slightly faster or even; three or more times, the previous PR is faster.  I decided the complexity of the cache wasn't worth it.  There's [a cleaned-up version of the caching implementation](https://github.com/jbosboom/cpython/commit/c2e6f81e4ab2a2cf2127ddb1c875278e862b13ff) on my fork if you want to take your own measurements.

(I also didn't test the cache in the free-threaded build; I think the atomics/locking is correct, but I don't really understand how critical sections that can be "suspended" can possibly be safe.)
```

```text
I can summarize my objection to mask=0 as a default.  How would a program use the result of `os.statx(f, 0)`?  If it needs anything more than the five unconditional members, it needs to check `stx_mask` to see if the result was filled in, e.g., `stx_mask & os.STATX_SIZE` if it needs the size.  What will the program do if that test is false?  The only think I can think of is to then call `os.statx(f, os.STATX_SIZE)` to actually get the size.  But then it should have specified `os.STATX_SIZE` in the mask in the first call.

When mask=0, [NFS will only return cached members](https://github.com/torvalds/linux/blob/0739473694c4878513031006829f1030ec850bc2/fs/nfs/inode.c#L1026), and [size may not be cached](https://github.com/torvalds/linux/blob/0739473694c4878513031006829f1030ec850bc2/fs/nfs/inode.c#L957).  So not getting the size isn't just a hypothetical situation.

> I don't know why [btrfs] doesn't return mtime and ctime by default.

mtime and ctime not being filled in unless requested also happens on xfs and ext4.  These three filesystems set `FS_MGTIME` to indicate they support [multigrain timestamps](https://lwn.net/Articles/946394/).  Since kernel version 6.13, the kernel will use finer-grained timestamps for files that have had their mtime or ctime queried recently, to ensure that all updates are detectable by looking at the mtime or ctime, at the cost of some atomic operations on a system-global variable.  [Here's the relevant kernel code that skips mtime and ctime if not in the mask.](https://github.com/torvalds/linux/blob/0739473694c4878513031006829f1030ec850bc2/fs/stat.c#L49)

I think this shows that callers of `os.statx` should provide an explicit mask of exactly the members they need, because even on local filesystems the kernel can optimize by returning only what's requested.
```

That means Arch has `stx_dio_read_offset_align` in `struct statx` and Debian currently doesn't.

```text
If we have `struct statx` at all, we know it has the members it has in kernel 4.11 (which introduced statx), so we can reference those members by name.  All members defined afterward may or may not be present, so we reference those members by offset.

To be clear, `struct statx` is the same regardless of architecture or 32/64-bitness.  The offsets don't change.  We just may not have the names for those offsets if we're building against old headers.

Runtime kernel support is handled via `mask` and `stx_mask`.  If userspace passes bits in `mask` that the running kernel doesn't know about, that's fine, it just never sets them in `stx_mask`.  If we omit members, we wouldn't be omitting them on "old kernels"; we'd be omitting them in CPython binaries built using old kernel API headers, regardless of the runtime kernel version.

If we want to avoid hardcoded offsets, we have these options:

- We could provide these members only if they are present at configure time.  Then we have to document that, and there's no precedent for "Availability: Python built with Linux kernel userspace API headers version >= 5.8" (for `stx_mnt_id`, different for other new members).  I think it would be hard to explain to users that `os.statx_result` may have more members on Arch (which ships new kernel API headers very quickly) than on Debian (which stays on LTS releases).

- Omitting `os.statx` if any member is missing is worse.  Debian currently ships headers from 6.12 that don't have `stx_dio_read_offset_align`, so Python built on Debian wouldn't get `os.statx` at all.  I expect Debian to be shipping the next LTS kernel by the time Python 3.15 releases, but the kernel may have added more members to statx by then too.  The point remains that any distro that's behind for any reason wouldn't get `os.statx` at all.

- We could make the latest kernel headers a build-time dependency, so that we always have all the member names.  This is essentially asking distro maintainers to build CPython differently than other packages.  I think the mainstream distros could handle this (if it didn't upset them), but it would be a problem for people building for embedded.

- If we had a minimum kernel version, we could provide only those members in that minimum version.  That would defeat the purpose of statx's extensibility, and anyway [there's no consensus for a minimum kernel version](https://discuss.python.org/t/minimum-supported-linux-kernel-and-glibc-versions/).

- We could provide only members present in kernel 4.11, because we always have those names.  Again this defeats the purpose of statx's extensibility.  Without agreement on a minimum kernel version, we can't ever expose more members.

- We could provide our own definition of `struct statx` copied from the latest kernel headers under a different name (say, `struct _Py_statx`).  Our definition would always have the members we care about regardless of the headers in the build environment.  It would be undefined behavior to use our definition with glibc's statx wrapper function, so we'd have to use `syscall(2)`, but not using the wrapper also means we're no longer dependent on the runtime glibc version.  (Currently we weakly link to the wrapper to support old glibc at runtime; if we took this option, we wouldn't link to the wrapper at all.)

I think that hardcoding offsets is better than these options.  `os.statx_result` in CPython version 3.x.y has the same members no matter how it was built (if it has `os.statx` at all).  We can easily add new members as soon as the kernel defines them.  We can use glibc's statx wrapper function instead of making an explicit syscall via `syscall(2)`.  The only cost is that we have to get the offset correct when we add a member (easy using the output of `pahole statx` on a kernel having the new member, no math required).
```

```text
This API is uneasy to use. It took me a while to understand `statx_result.stx_mask`: all attributes seem to be available, but the value of most attributes is zero. It's surprising. Since we have `stx_mask`, we could make `statx_result` less surprising: either remove attribute if they are missing from `stx_mask`, or set their value to `None` instead of `0`. I looked at the implementation and it might be possible to pack `(mask, offset)` as the *context* in `pystatx_result_getset` getters functions. *mask* is an unsigned int which can be 32-bit on 32-bit systems (32-bit pointers), which doesn't leave enough space for the 16-bit *offset* :-(

To make the implementation simpler, I suppose that we should leave `statx_result` as it is: always expose all attributes, but set their value to `0` if they are missing from `stx_mask`. The C API (statx) is the same and Python usually makes `os` functions as thin wrappers to the C API.
```

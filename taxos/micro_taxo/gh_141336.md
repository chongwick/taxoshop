#### Description

```text
Fixes assertion failure in Unicode escape decoding when using custom error handlers that return single-character replacements and rewind input position.

## Root Cause

The issue occurs in unicode_decode_call_errorhandler_writer() when:
1. Error handler returns a replacement string of length 1 (replen == 1)
2. Error handler rewinds input position (increasing remaining input bytes) 
3. Original code failed to account for replacement length in buffer calculations

This led to assertion failures in debug builds.

## Fix

- Always include full replacement length in writer.min_length calculations
- Change condition from replen > 1 to replen > 0
- Add full replen instead of replen - 1 to maintain buffer invariant
```

```text
I think the issue comes from how the error handler return value is accounted for in the unicode-escape / raw-unicode-escape decoder path.

When the custom error handler returns a replacement string and also rewinds the input (so that more input remains to be processed), the decoder needs to ensure there is enough room for:

1. The entire replacement string, and
2. The newly increased "remaining input" that will be decoded next.

Currently, the helper only adds (replacement_length - 1) to the required buffer size. That works only if the caller already pre-reserved space for exactly one output character, which isn’t true here. So in cases where the replacement length is exactly 1 and the input is rewound, the buffer ends up short by 1 character → leading to the assertion failure.

The correct behavior is to always account for the full replacement length when updating writer.min_length, along with any delta in remaining input. That ensures the writer capacity stays consistent with the decoder’s assumptions across all callers.
```

````text
@serhiy-storchaka I think the core idea here is to avoid growing the buffer every time and instead only do so when it is actually needed. The goal is to keep the assertion safe when the error handler rewinds the position, without introducing unnecessary overallocation in the normal path.

The way I am thinking about it is:

```
required = writer->pos + replen + new_remaining;
if (required > writer->min_length) {
    writer->min_length = required;
}
```

So the buffer only grows when this lower bound is larger than the current minimum. In cases where replen == 1 and there is no rewind, it should not trigger any extra allocation. And when the error handler rewinds input, this should still ensure the writer has enough room so the assertion remains valid.

On the infinite loop concern with rewinding, I agree that is a broader behavioral question. Here I am only focusing on making sure the writer capacity stays consistent so the crash does not occur. I may be missing something.
````

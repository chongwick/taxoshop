#### Description

```text
This PR fixes a sequential consistency bug (introduced by yours truly) whereby two threads that are deleting a struct member may observe both their deletions to be successful.

In order to test this properly, I couldn't use `threading.Barrier` because its overhead was enough to mask the bug, making the test flaky. Therefore, a spinning-loop barrier was added in the `_testcapi` module.
```

````text
# Bug report

### Bug description:

In #119368+#123211, member descriptors (related to user-defined slots) were made thread-safe. But not everywhere. The branch related to deletion remained unchanged:

https://github.com/python/cpython/blob/83360b5869a4981c87dcb59d1186d26c41fe3386/Python/structmember.c#L174-L187

Since threads perform the check (`addr == NULL`) in a non-thread-safe manner, the operation may succeed even if it has already been executed by another thread. At the Python level, this means that an `AttributeError` may not be raised during two or more concurrent attempts to delete an attribute, and as a result, code that was supposed to execute only once (after a successful deletion) will be executed more than once.

The behavior matches what is expected on CPython with GIL and on PyPy (and possibly other interpreters), but not on CPython without GIL. Without slots (using `__dict__`), the behavior also matches what is expected even in free-threading. Meanwhile, user-defined slots [already rely on critical sections](https://github.com/python/cpython/blob/83360b5869a4981c87dcb59d1186d26c41fe3386/Python/structmember.c#L332-L338), so the simplest solution would be to move the check for `Py_T_OBJECT_EX` under the critical section (into the case block).

Code to reproduce (`del obj.b` raises an `AttributeError`):

```python
#!/usr/bin/env python3

import time

from concurrent.futures import ThreadPoolExecutor


class ObjectWithSlots:
    __slots__ = (
        "a",
        "b",
    )

    def __init__(self):
        self.a = None
        self.b = None


def main():
    def test():
        try:
            del obj.a
        except AttributeError:  # not the first thread
            pass
        else:
            del obj.b

    with ThreadPoolExecutor(2) as executor:
        start = time.perf_counter()

        while time.perf_counter() - start < 1:  # one second
            obj = ObjectWithSlots()

            f1 = executor.submit(test)
            f2 = executor.submit(test)

            f1.result()  # reraise
            f2.result()  # reraise


if __name__ == "__main__":
    main()
```
````

```text
Behavior that occurs in free-threading:

1. Suppose both threads have entered `PyMember_SetOne()`.
2. Thread A checks `addr == NULL`, gets `false`, but sleeps before `FT_ATOMIC_STORE_PTR_RELEASE()`.
3. Thread B also checks `addr == NULL` and also gets `false` (since Thread A did not have time to change the value of `addr`).
4. The rest of this story is of no interest to us: neither of these threads will raise an `AttributeError` at `del obj.a`, and as a result, both threads will attempt to do `del obj.b` (and either enter a race condition again, or one of them will raise an `AttributeError`).

A classic scenario, nothing new. Incorrect sequences such as `if not loop.is_closed(): loop.call_soon_threadsafe(...)` also have this nature (unfortunately, I sometimes see this in various projects; here it would be better to use a try-except on `RuntimeError` instead, since otherwise the event loop may close before the call but after the check), and everything else that for some reason tries to use simple checks in a multithreaded environment.
```

```text
I should note that it would be possible to handle both `__set__()` and `__delete__()` without per-object locks, simply by using something like `_Py_atomic_exchange_ptr()` from `pyatomic.h` (and raising an `AttributeError` when both the new and old values are `NULL`). There is no wrapper for it in `pycore_pyatomic_ft_wrappers.h`, but as I saw in one PR, it can be used with `#ifdef Py_GIL_DISABLED`.

---

Oh, wait, I saw the comments about this in the discussion of the first PR mentioned. Never mind.

---

Hypothetically, it could be used reliably in `PyMember_SetOne()` if it were also used in `PyMember_GetOne()`: the getter would exchange the value with some special value, thereby preventing the setter from performing a decref. It would then attempt a compare-and-exchange back, and perform an incref only if successful. That way, only the getters would have to be synchronized. But this is a dubious benefit, and support for the special value would also have to be handled by C API users (or not? if they always use per-object locks or if some special value is safe, then the new behavior would not make any difference except for the possibility of concurrent writes while holding the lock, but I know too little about C API use cases). So yes, it seems that there is not much that can be done here.

On the other hand, the technique I described optimizes my use case (`slot.__delete__()` as an atomic Python-level test-and-set). The optimistic path of `PyMember_GetOne()` is not going anywhere, so in the best-case scenario (read-only or write-only), all operations will be performed without per-object locks. But there is the problem with the special value...
```

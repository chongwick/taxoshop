````text
# Bug report

### Bug description:

#131336 / #128182  made `ctypes.resize` and `addressof`/`byref` thread-safe by taking a critical section in `_ctypes_resize`, which reallocates `obj->b_ptr`:

https://github.com/python/cpython/blob/a2a846678e54b1b5defdccd451c573679094ff02/Modules/_ctypes/callproc.c#L1875-L1935

But the buffer-protocol getbuffer, `PyCData_NewGetBuffer` (reached via `memoryview(cdata)`), reads `self->b_ptr` **without** that critical section:

https://github.com/python/cpython/blob/a2a846678e54b1b5defdccd451c573679094ff02/Modules/_ctypes/_ctypes.c#L3103-L3130

So `memoryview(obj)` racing `ctypes.resize(obj)` reads a `b_ptr` that `resize` concurrently reallocates.

Reproducer:
```python
import ctypes
from threading import Thread

buf = (ctypes.c_char * 64)()

def viewer():
    for _ in range(20000):
        try:
            memoryview(buf)
        except Exception:
            pass

def resizer():
    for i in range(20000):
        try:
            ctypes.resize(buf, 128 if (i & 1) else 256)
        except Exception:
            pass

threads  = [Thread(target=viewer)  for _ in range(6)]
threads += [Thread(target=resizer) for _ in range(2)]
for t in threads: t.start()
for t in threads: t.join()
```
````

````text
This race is **memory-unsafe**, not value-benign — it escalates to a crash. The exported `b_ptr` that `PyCData_NewGetBuffer` reads is the live buffer pointer; while a `memoryview` holds it, `ctypes.resize()` reallocates and frees it, so a write (or read) through the view hits freed heap and corrupts the allocator.

Reproducer (crashes ~every run on a free-threaded `--with-address-sanitizer` build of `main`, `PYTHON_GIL=0`):

```python
import ctypes, threading
buf = (ctypes.c_char * 64)()
N = 60000
def viewer():
    for _ in range(N):
        try:
            mv = memoryview(buf).cast('B')
            mv[:] = b'\xff' * len(mv)          # write through the exported (maybe-freed) b_ptr
            mv.release()
        except Exception:
            pass
def resizer():
    for i in range(N):
        try:
            ctypes.resize(buf, (1 << 20) if (i & 1) else 64)   # realloc frees/moves b_ptr
        except Exception:
            pass
ts = [threading.Thread(target=viewer) for _ in range(6)] + \
     [threading.Thread(target=resizer) for _ in range(6)]
for t in ts: t.start()
for t in ts: t.join()
```

The SEGV lands inside `_ctypes_resize` itself — its realloc trips over the freelist that the racing write-through-the-stale-export corrupted:

```
AddressSanitizer: SEGV ... in mi_block_nextx            (mimalloc freelist traversal)
  ... _mi_heap_realloc_zero   Objects/mimalloc/alloc.c:732
  _ctypes_resize_impl         Modules/_ctypes/callproc.c:1925
  _ctypes_resize              Modules/_ctypes/clinic/callproc.c.h:139
```

On a TSan build the same script also reports the write side racing the buffer memory (`__tsan_memcpy` ← `copy_base` `Objects/memoryobject.c:353` ← `memory_ass_sub`), complementing the read-side report (`PyCData_NewGetBuffer:3129`) in the issue.

**A second, related gap (deterministic, no threads):** `ctypes.resize()` doesn't refuse a cdata that has **live buffer exports**, so even single-threaded it frees a still-exported buffer (feel free to open an issue for that or tackle it here):

```python
buf = (ctypes.c_char * 64)()
mv = memoryview(buf)          # live export
ctypes.resize(buf, 4096)      # succeeds — no BufferError
bytes(mv[:8])                 # reads freed memory (0xdd... DEADBYTE on a debug build)
```

Edit: On a GIL `--with-address-sanitizer` build with `PYTHONMALLOC=malloc` this aborts deterministically (every run) with a clean use-after-free naming the alloc / free / access:

```
AddressSanitizer: heap-use-after-free ... READ of size 8
    #1 PyBuffer_ToContiguous   Objects/memoryobject.c:1063        (bytes(memoryview(buf)))
    #2 _PyBytes_FromBuffer     Objects/bytesobject.c:2974
  freed by thread T0 here:
    #0 realloc
    #1 _ctypes_resize_impl     Modules/_ctypes/callproc.c:1925    (resize freed the exported buffer)
  previously allocated by thread T0 here:
    #1 PyCData_MallocBuffer    Modules/_ctypes/_ctypes.c:3293
    #2 generic_pycdata_new     Modules/_ctypes/_ctypes.c:3611
```

`bytearray`/`array.array` raise `BufferError: Existing exports of data: object cannot be re-sized` here; ctypes has no such guard. The critical-section fix on `PyCData_NewGetBuffer` closes the concurrent race but wouldn't address this — `_ctypes_resize` also needs an export/`b_locked`-count check before it reallocates. Might be worth handling both together.
````

```text
@devdanzin 
I've been investigating this issue.

From looking at the implementation:

- `PyCData_NewGetBuffer()` exports `b_ptr`/`b_size` without synchronization.
- `_ctypes.resize()` is already protected by `@critical_section obj`.
- `CDataObject` currently has no export counter or `bf_releasebuffer` implementation.

The comment above also demonstrates a deterministic single-threaded use-after-free when resizing with a live `memoryview`, which wouldn't be addressed by synchronizing `PyCData_NewGetBuffer()` alone.

Would you prefer a fix limited to the free-threaded race, or should a patch also add export tracking so `ctypes.resize()` raises `BufferError` while buffers are exported (similar to `bytearray`/`array.array`)?
```

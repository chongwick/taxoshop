### Original Issue

Source: [https://github.com/python/cpython/issues/113956](https://github.com/python/cpython/issues/113956)

````text
# Bug report

### Bug description:

The code in `_Py_SetImmortal` must be run on the thread that originally allocated the object. If this is not the case, then a race between `Py_INCREF` can cause the `_Py_SetImmortal` to be ignored.

https://github.com/python/cpython/blob/2e7577b622616ef5ff2d1460fb5bebf845f0edf3/Include/internal/pycore_object.h#L128-L139

Example sequence:

1.  Allocating thread begins an `_Py_Incref`.
2.  Allocating thread detects it should perform inc ref on `ob_ref_local`, and calculates new value.
3.  Non-allocating thread runs all of `_Py_SetImmortal`.
4.  Allocating thread completes incref with assignment to `ob_ref_local`, and unsets the value from immortal.

In the nogil fork, there is some defensive code on other operations that need to be run on the allocating thread, e.g.

```C
_PyObject_SetDeferredRefcount(PyObject *op)
{
    assert(_Py_ThreadLocal(op) && "non thread-safe");
```
https://github.com/colesbury/nogil-3.12/blob/cedde4f5ec3759ad723c89d44738776f362df564/Include/internal/pycore_object.h#L361C19-L361C19

I think something like this should occur inside `_Py_SetImmortal`.

It looks like `_Py_SetImmortal` is not exposed outside the runtime.  However, [PEP 683](https://peps.python.org/pep-0683/#specification), says:

> Then setting any object’s refcount to _Py_IMMORTAL_REFCNT makes it immortal.

This implies there is an intent to expose it, and with the changes to nogil.  It seems that this should be exposed as an explicit operation, rather than by setting the ref count directly. 

CC @ericsnowcurrently @colesbury

P.S. I am happy to PR any required changes.
````

```text
A few thoughts:

- Yes, if the owning thread calls `Py_INCREF()` concurrently with another thread trying to immortalize the object, that will result in a race condition
- `_Py_SetImmortal()` is not public and I don't think we should make it public (at least not in 3.13)
-  The check that the caller is the owning thread is conservative. It's also safe to immortalize objects in certain other cases, such as during a stop-the-world event.
```

```text
I would be hesitant to add an assertion to `_Py_SetImmortal()` because we call it from a number of places where we already know we are in a bad state, like [`none_dealloc`](https://github.com/python/cpython/blob/2e7577b622616ef5ff2d1460fb5bebf845f0edf3/Objects/object.c#L1935-L1943). 

The only call I've seen that concerns me is in [`_PyUnicode_InternInPlace()`](https://github.com/python/cpython/blob/2e7577b622616ef5ff2d1460fb5bebf845f0edf3/Objects/unicodeobject.c#L14923). In the free-threaded builds, we should probably only immortalize the string if it is owned by the current thread.
```

```text
> I think you could make it concurrency safe by borrowing a third bit from ob_ref_shared to represent Immortal.

Yeah, that would address concurrency safety, but using `ob_ref_local` serves two other purposes:

1) It let's us make `ob_ref_local` 32-bits without having to worry about overflow, because the immortal value is `UINT32_MAX`.
2) It makes the common cases for `Py_INCREF` and `Py_DECREF` faster because we only need to access `ob_tid` and `ob_ref_local`.
```

````text
Adding a concrete reproducer for this race. The scenario @mjp41 described and @colesbury confirmed above is reachable from pure-Python code via concurrent `setattr()` on shared objects with fresh string keys — exactly the `_PyUnicode_InternInPlace` caller Sam flagged as the concerning one.

## Reproducer (pure stdlib, no extensions)

```python
import os
import signal
import sys
import threading
import time

N_THREADS = 8
N_ITERS = 500
N_KEYS_PER_ITER = 5
SCENARIO_TIMEOUT = 120


class Target:
    pass


def scenario():
    for i in range(N_ITERS):
        target = Target()
        # Fresh strings via concatenation — NOT bytecode literals, so they
        # aren't already interned-immortal when the threads start.
        keys = [
            "tsan_intern_race_probe_" + str(i) + "_" + str(j)
            for j in range(N_KEYS_PER_ITER)
        ]
        values = list(range(N_KEYS_PER_ITER))
        barrier = threading.Barrier(N_THREADS)

        def worker():
            barrier.wait()
            for k, v in zip(keys, values):
                try:
                    setattr(target, k, v)
                except Exception:
                    pass

        threads = [threading.Thread(target=worker) for _ in range(N_THREADS)]
        for t in threads:
            t.start()
        for t in threads:
            t.join()


# Run in a forked subprocess so a crash doesn't take down the parent.
pid = os.fork()
if pid == 0:
    try:
        scenario()
        os._exit(0)
    except Exception:
        os._exit(1)

deadline = time.monotonic() + SCENARIO_TIMEOUT
status = None
while time.monotonic() < deadline:
    r, s = os.waitpid(pid, os.WNOHANG)
    if r != 0:
        status = s
        break
    time.sleep(0.1)

if status is None:
    os.kill(pid, signal.SIGKILL)
    os.waitpid(pid, 0)
    print("TIMEOUT")
elif os.WIFSIGNALED(status):
    print(f"CRASH ({signal.Signals(os.WTERMSIG(status)).name})")
elif os.WIFEXITED(status) and os.WEXITSTATUS(status) != 0:
    print(f"FAIL (exit {os.WEXITSTATUS(status)})")
else:
    print("OK")
```

## Notes

- Not reproducible (user-visibly) on a release FT build — the consistency check is compiled out. The underlying data race still exists and TSan still flags it.
- Not reproducible on a GIL build (serialized access to the interning path).
- The 3.15 reproduction is with ASAN, no TSan — so the SIGABRT is not a TSan instrumentation artifact. It's a natural consequence of the program flow violating the `SSTATE_INTERNED_MORTAL` → `!immortal` invariant.
- Both test builds include the reordering from gh-146072 (merged 2026-03-24), which moved `_Py_SetImmortal(s)` to execute **before** the atomic publication of `SSTATE_INTERNED_IMMORTAL`. The comment added in that PR explicitly documents the ordering as the synchronization point for `intern_common`'s lock-free fast path — which makes the race window visible in the source. I don't think gh-146072 *introduced* the race (the `Py_INCREF` at `PyObject_SetAttr:1449` has always been concurrent with `immortalize_interned` under the lock), but the new layout makes it easier to reason about.
- The comment in `_PyUnicode_CheckConsistency` (`Objects/unicodeobject.c:760-763` on 3.14, `:675-676` on 3.15) calls the "object observed in INTERNED_MORTAL state turns out to be immortal" case "extremely unlikely (worth a potential failed assertion in a debug build)." The reproducer above suggests "extremely unlikely" is too strong — 8 threads and a fresh key per iteration is enough to hit it on first try.

No fix proposed — I'm not familiar enough with the FT internals to judge between making the writes atomic, relaxing the debug assertion, or requiring the owning-thread discipline Matthew originally suggested. Happy to provide full TSan output or test any candidate fix.

Found while investigating TSan results from a C extension (`wrapt`) using [labeille](https://github.com/devdanzin/labeille) and [ft-review-toolkit](https://github.com/devdanzin/ft-review-toolkit); isolated to pure stdlib after ruling out the extension's own races.
````

Your test calls `addop` improperly.

If you fix your test to pass `0` and not `256` as the `oparg`:

```diff
<             ("TO_BOOL", 256, 1),
>             ("TO_BOOL", 0, 1),
```
it will no longer trigger the C-level assertion error.

That said, the underlying incorrect call is:
```py
seq.addop(39, 256, 1, -1, -1, -1)
```

It should be:
```py
seq.addop(39, 0, 1, -1, -1, -1)
```

`TO_BOOL` (opcode `39`) does not take an argument, but the test does the `addop` call with `256` as the `oparg` instead of the expected `0`.

That's precisely what the assertion says:

https://github.com/python/cpython/blob/3e36d375352632be85b9ac3a0eeb075a4e03ef6f/Python/instruction_sequence.c#L121

<details>

Any op has to either:
- take an argument (`TO_BOOL` doesn't) *or*
- be a jumping instruction (such as in `for`) or a "block-push" instruction (such as in `with`) (`TO_BOOL` doesn't) *or*
- receive `0` as the argument, which is valid for opcodes that don't take arguments (`TO_BOOL` expected `0`, but `256` was passed).

</details>

@iritkatriel, do you think that `InstructionSequenceType_addop_impl` should throw exceptions for incorrect calls before reaching `_PyInstructionSequence_Addop`? Or is this just invalid, and the caller is fully responsible for abiding the contract?
